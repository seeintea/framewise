# iOS 相机取景与成片一致性

> 状态：2026-09-19 发现严重取景一致性问题，当前修复实验未解决问题。
> 在完成统一坐标变换设计前，不把跨方向模板拍摄视为可交付能力。

## 1. 已确认的问题

当模板方向与手机拍摄方向不一致时，例如竖持手机使用 `4:3` 横版模板：

- 屏幕会为了最大化利用空间，以 `3:4` 竖向区域显示相机预览，并旋转构图模板。
- 最终文件仍需要遵循模板的 `4:3` 横版配置。
- 当前成片的方向、可见范围或内容朝向无法与快门前的取景画面保持一致。

这属于成像正确性问题，不是轻微的 UI 偏差。用户可以用任意持机方向拍摄任意模板，但最终
成片必须准确对应取景器承诺的内容。

## 2. 当前链路为什么不足

当前实现存在两套彼此独立的几何逻辑：

1. `CameraView` 根据屏幕尺寸，在模板原始比例及其倒数之间选择面积更大的预览区域，并可能
   单独旋转 `CompositionCanvas`。
2. `CameraPreview` 使用 `AVCaptureVideoPreviewLayer.resizeAspectFill` 显示相机内容。
3. 拍摄时 `AVCaptureDevice.RotationCoordinator` 只提供设备与传感器的输出方向。
4. `LivePhotoProcessor` 不知道预览层实际显示了传感器的哪个区域，只在方向归一化后的完整
   图片中央按模板比例裁切。

仅把模板的 `90°` 布局旋转加减到 capture connection 并不能解决问题。2026-09-19 的实验
证明，这会改变最终文件方向，但仍不能保证成片内容与预览一致，并可能让内容整体侧转。

## 3. 重建方向

后续成像链路应以“按下快门时的取景快照”为唯一事实来源，而不是分别推断预览与输出：

1. 建立明确的 `CameraFramingTransform`（名称待实现时确定），记录一次拍摄所需的完整几何
   信息：传感器方向、前摄镜像、预览 bounds、`videoGravity`、归一化可见区域、模板旋转、
   目标输出尺寸和裁切矩形。
2. 从 `AVCaptureVideoPreviewLayer` 的坐标转换能力得到真实可见区域，不能只根据宽高比假设
   中心裁切。
3. 静态照片与 Live Photo paired movie 必须消费同一份取景快照和仿射变换，禁止各自重新
   推导方向或裁切。
4. 模板方向决定最终文件方向；持机方向只决定用户当时如何查看和操作取景器。
5. 缩放、前后摄切换、镜像和设备旋转必须在按下快门时冻结，避免捕获期间状态变化导致错配。

## 4. 最低验收矩阵

每一种组合都需要对照明显位于四边和四角的参照物，确认预览与成片一致：

- `3:4` 模板：竖持、左横持、右横持。
- `4:3` 模板：竖持、左横持、右横持。
- 后摄与前摄，包含前摄镜像语义。
- 普通照片与 Live Photo 的静态图、配对视频。
- `0.5×`、`1×`、长焦及手势缩放。
- 模板方向与持机方向相同、相反两类路径。

验收不只检查输出宽高比和 EXIF 方向。必须确认预览边缘可见内容、主体位置、构图线位置与
最终照片逐一对应；允许由底层照片管线带来的极小视场差异，但不能出现明显二次裁切、偏移、
镜像错误或整幅侧转。

## 5. 当前检查点

本检查点保留了“将预览布局旋转角传入 capture connection”的实验代码，用于记录已经验证
无效的方向。它不是最终修复；下一步应先重新定义成像坐标模型，再替换这段实验逻辑。
